# UniListView Developer Guide

## Book 4. Showcase Studio

# Глава 11. Demo Packages --- модульная архитектура демонстрационных пакетов

------------------------------------------------------------------------

# Введение

По мере развития UniListView количество демонстрационных сцен неизбежно
растёт. Если все демонстрации хранить в одном проекте, он быстро станет
трудно сопровождаемым, увеличится время компиляции и усложнится
командная разработка.

Для решения этой проблемы Showcase Studio использует концепцию **Demo
Packages** --- независимых пакетов демонстраций, подключаемых к единому
ядру.

------------------------------------------------------------------------

# Цели модульной архитектуры

Demo Packages позволяют:

-   разделять большие коллекции примеров;
-   уменьшать связанность;
-   ускорять разработку;
-   подключать дополнительные наборы сцен;
-   распространять Showcase по частям;
-   поддерживать внутренние и публичные демонстрации.

------------------------------------------------------------------------

# Общая архитектура

    Showcase Studio
            │
            ▼
      Showcase Core
            │
     ┌──────┼──────────┐
     ▼      ▼          ▼
    Core  Charts   Enterprise
    Package Package Package

Каждый пакет содержит собственные сцены и регистрирует их через общий
Registry.

------------------------------------------------------------------------

# Состав пакета

Типичный пакет включает:

-   модуль регистрации;
-   набор сцен;
-   документацию;
-   ресурсы;
-   изображения;
-   локализацию;
-   тестовые данные.

Все внутренние детали пакета скрыты от остальных модулей.

------------------------------------------------------------------------

# Регистрация

При подключении пакет вызывает процедуру регистрации.

Во время регистрации передаются:

-   сведения о пакете;
-   список сцен;
-   категории;
-   зависимости;
-   поддерживаемые платформы.

После завершения регистрации пакет становится доступен Navigation и
Search Engine.

------------------------------------------------------------------------

# Независимость

Каждый пакет должен быть максимально автономным.

Он не должен напрямую обращаться к сценам другого пакета.

Обмен информацией выполняется только через публичные сервисы Showcase
Core.

------------------------------------------------------------------------

# Версионирование

Каждый пакет имеет собственную версию.

Рекомендуется хранить:

-   Version;
-   Build;
-   API Compatibility;
-   Required Core Version.

Это позволяет своевременно обнаруживать несовместимость.

------------------------------------------------------------------------

# Зависимости

Если пакет использует возможности другого пакета, зависимость должна
быть объявлена явно.

Например:

    Enterprise Package
        ↓
    Core Package

Циклические зависимости запрещаются.

------------------------------------------------------------------------

# Локализация

Каждый пакет может поставляться с собственными переводами.

Структура каталогов рекомендуется следующая:

    Package
     ├─ Scenes
     ├─ Docs
     ├─ Images
     ├─ Locale
     └─ Resources

Такое разделение упрощает сопровождение.

------------------------------------------------------------------------

# Ресурсы

Все ресурсы пакета должны храниться внутри него.

Например:

-   SVG;
-   PNG;
-   стили;
-   Markdown;
-   JSON;
-   демонстрационные данные.

Не рекомендуется использовать общие каталоги без необходимости.

------------------------------------------------------------------------

# Загрузка

Пакеты могут загружаться:

-   автоматически;
-   по конфигурации;
-   по запросу пользователя.

Это особенно полезно для больших корпоративных Showcase.

------------------------------------------------------------------------

# Обновление

При выпуске новой версии библиотеки отдельный пакет может обновляться
независимо.

Главное условие --- совместимость с API Showcase Core.

------------------------------------------------------------------------

# Расширение сторонними разработчиками

Архитектура должна позволять создавать внешние пакеты.

Например:

-   демонстрации заказчика;
-   корпоративные расширения;
-   учебные материалы;
-   внутренние лаборатории.

При этом ядро Showcase Studio остаётся неизменным.

------------------------------------------------------------------------

# Контроль качества

Перед регистрацией рекомендуется проверить:

-   корректность идентификаторов;
-   наличие документации;
-   уникальность сцен;
-   совместимость версии;
-   наличие обязательных ресурсов.

Ошибки должны выявляться до открытия первой сцены.

------------------------------------------------------------------------

# Лучшие практики

Рекомендуется:

-   делать пакеты небольшими;
-   избегать скрытых зависимостей;
-   использовать единый стиль оформления;
-   хранить документацию рядом со сценами;
-   обеспечивать обратную совместимость API.

------------------------------------------------------------------------

# Антипаттерны

Следует избегать:

-   хранения общих ресурсов в нескольких пакетах;
-   циклических зависимостей;
-   регистрации сцен вручную в разных местах;
-   прямого обращения к внутренним классам другого пакета.

------------------------------------------------------------------------

# Итоги

Demo Packages превращают Showcase Studio в масштабируемую платформу.
Благодаря модульной архитектуре демонстрации можно развивать независимо,
подключать по мере необходимости и сопровождать отдельными командами без
изменения ядра приложения.

Следующая глава будет посвящена созданию собственной демонстрационной
сцены: структуре класса, требованиям к коду, регистрации, документации и
рекомендациям по разработке новых примеров.
